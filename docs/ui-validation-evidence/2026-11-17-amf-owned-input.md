# AMF owned-input pipeline candidate

Status: source regression checks passed; hardware acceptance is pending. The installed beta.14 is not accepted as the high-refresh fix.

The previous path waited for capture-to-encoder keyed-mutex ownership, conversion and encoded output in the capture loop. The replacement keeps two owned BGRA inputs on the original adapter and two submitted codec frames. It issues the capture copy while the DesktopDup surface is valid, then polls cross-device ownership with zero timeout. AMF only receives its own NV12 frames. An input rejected with EAGAIN remains prepared for retry; admission stops before consuming another DesktopDup frame when both owned slots are unavailable. Polling also drains the final static frame without requiring another capture.

GPU synchronization has not been removed. Every keyed-mutex acquire requires S_OK, including the positive WAIT_TIMEOUT/WAIT_ABANDONED statuses. Slot construction commits only complete resources. Existing one-second GPU/codec progress limits remain bounded; codec errors are retained. Display-change retirement still drains the codec and confirms both GPU contexts before releasing owners. This change neither creates nor removes displays, changes primary output, installs drivers, changes streaming bitrate policy, nor changes network authorization.

Regression surface: the Windows AMF implementation in ffmpeg_vram_encode.cpp and its new fixed-size input metadata; its FFI declaration/binding and Windows VRamEncoder readiness forwarding; a default readiness method on the erased EncoderApi trait; and the GPUI Windows video loop's pre-capture admission/pacing hook. The trait hook is required because the capture loop owns a dynamically dispatched EncoderApi, and other encoders retain their ready-by-default path. Windows VRAM compilation selects C++17 for the optional input state; other targets keep their existing compiler settings. The existing AMF CPU regression command now checks queue saturation, GPU-busy slot reuse, ordered retry and static-tail delivery. The Windows host workflow runs that command and the existing retirement checks even for build-only candidates.

Validation: AMF owner latch, bounded input queue, AVC/HEVC parameter-set/error propagation, dynamic peak-rate regression and all three existing CPU retirement tests passed with Clang. Rust formatting was inspected with the installed formatter: remaining differences are untouched pre-existing lines. Product compilation and local capture/encode/receive/decode/UI/actual-present measurements must still pass. Queue tests cannot establish GPU concurrency, visual quality or a hardware frame-rate result.

## Refresh-switch regression reproduced on the installed beta.14

At 11:32:55, the newly created hevc_amf texture encoder reported `gdi: false`, then `No image, fall back to gdi` only 69 ms later. It immediately restarted through CaptureBackendChanged. The GDI fallback marker subsequently excluded VRAM encoders even when DXGI produced frames again. Later metrics confirm RAM frames at 40–53 FPS and GDI/RAM at approximately 20–24 FPS despite the target remaining 8.333 ms. This is a capture-path downgrade, not a confirmed Android refresh cap or network adaptation event.

GPUI now leaves normal WouldBlock results on the current capture path; real capture errors retain the bounded DXGI recovery/GDI fallback and existing GPU retirement requirements. A successful DXGI image clears the recovery marker after any initial no-frame attempts, rather than only if it was the first attempt. This also prevents the new pre-capture backpressure signal from being mistaken for a broken capturer. Local acceptance must include repeated rate switches and verify that the texture path remains active.
