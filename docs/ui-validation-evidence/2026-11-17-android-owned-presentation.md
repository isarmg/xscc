# Android presentation investigation

Status: beta.18 owned-image worker failed hardware performance acceptance and has been removed. The next candidate selects Android Mailbox presentation only when the actual surface reports support; hardware acceptance is pending. No high-refresh completion claim.

Installed host beta.17 eliminated the false normal-WouldBlock-to-GDI downgrade. Native Windows mode reads verified the existing DISPLAY40 at 90, 144, 240 and back to 120 Hz, while physical DISPLAY1 remained primary at 60 Hz. Android beta.14 receive/decode/UI medians were 89/89/89 at 90 Hz, 110/111/89 at 144 Hz, 112/112.5/89 at 240 Hz, and 118/118/89 after returning to 120 Hz. These validate the refresh-switch regression, not Android UI performance acceptance. No driver change or virtual-display creation/removal occurred.

With beta.18 at the same 1080p/120Hz UFO workload, the minute-long closed-menu sample measured receive/decode/UI medians 114.5/113.5/88 FPS; steady SurfaceFlinger windows were 88.95/89.48/88.96 Hz. The worker moved about 7 ms of blocking native presentation into the next texture upload (median upload 7.86 ms versus beta.14 about 1.06 ms). Pinned wgpu-core Queue::present holds device.command_indices exclusively around native presentation; keeping a separate worker on that same queue therefore did not remove serialization. The two-image pool, surface-worker lifecycle hooks and extra copy have been removed instead of retained as ineffective complexity.

The physical Xiaomi 13 startup log reports Vulkan Adreno 740 with supported modes [Mailbox, Fifo]; the old selection was Fifo. The next candidate selects Mailbox on Android when supported, leaving an explicit supported preference unchanged and falling back to the original Fifo path otherwise. Mailbox uses display-synchronized latest-frame presentation rather than a FIFO of stale frames. No wgpu synchronization locks, driver guarantees, decoder or system refresh-rate settings are modified.

Regression surface: only Android default native-surface mode selection changes. Existing native acquire/render/present ownership and lifecycle resume. Non-Android platforms keep Fifo defaults; Android surfaces without Mailbox keep Fifo. Packaging versionCode increments to 40019. Required physical regression checks are actual presentation versus receive/decode/UI at 90/120 and 144/240 remote modes, background/resume, orientation and reconnect.

## Device-progress lock correction candidate (beta.20)

Beta.19 Mailbox was physically confirmed and reduced native present medians to approximately 0.85 ms in the first minute, with receive/decode/UI medians 116.5/116/105.5 FPS. Actual presentation windows ranged about 95-117 Hz. It improved the 89Hz plateau but did not meet sustained acceptance; a later profile still showed variable native waits (present median about 5.18 ms). No high-refresh completion claim is made.

Inspection of pinned wgpu Device::maintain identified the missing overlap dependency in beta.18: even PollType::Poll takes command_indices.read(), which waits for Queue::present's command_indices.write(). The Android image upload performed that poll before copying any pixels, so the supposedly non-waiting completion poll serialized scene recording behind the previous native present. Beta.20 relocates that exact completion poll to the bounded presentation worker, after presentation and before returning image credit. The two owned images and lifecycle drains now let the UI prepare/copy/record the next scene before the final queue submit synchronization. Existing wgpu locks and GPU ownership remain intact; no upstream dependency patch or unsynchronized submission was introduced. Mailbox selection from beta.19 is retained.

New regression surface beyond the beta.18 candidate: Android ImageUpload no longer progresses device maps itself; every presentation worker iteration progresses them, including surface timeout/retry results. Render errors return image credit; drain/reconfigure/drop retain the existing bounded worker lifecycle. All non-Android paths are unchanged. Full ARM build and hardware acceptance are pending for this correction.

## Beta.20 hardware rejection

The device-progress relocation did remove the UI upload wait (median upload 0.81 ms), but the same serialization reappeared at the final scene queue submission. The worker's full acquire/copy/present/progress cycle remained about 10.63 ms. The one-minute 120Hz sample measured receive/decode/UI medians 99.5/99/86 FPS; SurfaceFlinger measured 86.87/87.89/88.93 Hz. This correction did not meet acceptance and is removed. The last simpler Mailbox path is retained for the next package; no worker/image pool or custom lifecycle hook remains. Further work must avoid driving every video frame through the same UI/native present queue rather than relocating that wait again.
