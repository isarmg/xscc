# Android owned rendering/presentation candidate

Status: hardware acceptance pending. Do not label the high-refresh task complete.

Installed host beta.17 uses the GPU texture path without the false WouldBlock-to-GDI downgrade. With the unchanged Android beta.14 at 1080p/120Hz, the one-minute closed-menu sample recorded median receive/decode/UI acceptance of 116/116/89 FPS. Actual SurfaceFlinger short windows also measured approximately 89 Hz. CPU rendering averaged approximately 2.44 ms and native presentation blocked for approximately 7.28 ms on the same UI thread. The panel and layer both requested 120 Hz; no frame-rate override or thermal status restriction was reported. A 90Hz remote mode reached median 89/89/89 FPS rather than falling back to the previous 20–50 FPS RAM/GDI path. Other rate switches still need validation.

The Android renderer now builds each scene into one of two owned GPU images. A bounded worker owns native swapchain acquire, copy/blit, and presentation. This allows scene preparation and GPU command recording to overlap the native presentation wait instead of paying both serially on the UI thread. The same wgpu device/queue maintains submission ordering and owns GPU resource retirement; no raw pointers or unsynchronized texture sharing were added. Platforms other than Android retain their surface drawing path.

At most two owned images and one queued presentation request exist. Render errors return their image credit. Resize, transparency change, detach, replacement, recovery and destruction drain outstanding requests before touching native surfaces. Worker failures wake the existing Android event loop for redraw/error handling; recovery retains that wake connection. COPY_DST is requested only when the native surface reports support; otherwise wgpu's texture blitter performs the copy. The decoder, keyboard, controls, orientation request, audio, font and Windows driver are unchanged.

Measurement semantics: android_gpu_pipeline now calls the producer wait present_enqueue_ms. android_present_pipeline separately reports the worker's real acquire/copy/present wall time. UI acceptance remains distinct from SurfaceFlinger actual presentation. Required physical checks are sustained receive/decode/UI/actual presentation, repeated 90/120/144/240Hz remote switches, background/resume, rotation and reconnect without validation errors or retained old frames.
