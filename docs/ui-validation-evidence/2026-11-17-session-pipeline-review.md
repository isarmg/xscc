# 串流运行管线审查（2026-11-17）

状态：审查和整体设计，尚未完成实现，性能验收未通过。不得把 beta.14 标为稳定高刷修复。

## 已确认的实现约束

1. `src/server/video_service.rs` 在同一轮依次执行捕获、编码、发送交接等待和节拍等待。`vendor/hwcodec/cpp/ffmpeg_vram/ffmpeg_vram_encode.cpp` 的 AMD 路径还有跨设备 keyed mutex 等待与编码输出等待。增加在途帧数没有消除这些串行依赖；也不得为提速删除 GPU 所有权保护。
2. `crates/session-model/src/lib.rs` 的 FrameBuffer 强制要求 AsRef<[u8]>。`libs/scrap/src/common/mediacodec.rs` 读取输出字节、转换为 RGB，再释放解码缓冲；`crates/native-ui/src/presentation.rs` 和 Android atlas 随后重新上传。目录拆分没有实现解码输出到呈现的原生表面通路。
3. 传输层具备 session/epoch/frame_id 校验，但 `crates/session-transport/src/lib.rs::deliver` 向上返回的是媒体负载。GPUI Frame 只携带 display、像素和本地 metrics_epoch，缺少贯穿捕获、编码、传输、解码和呈现的同一帧身份，当前分段统计难以准确配对。
4. `VideoFrameController` 等待的是 display/connection 通知；通知携带的时间只用于日志，cur 不参与确认匹配。它不等于绑定具体帧和代次的发送信用。UDP 发送队列已有独立边界，继续保留旧式逐轮交接等待会使背压责任分散；不能只添加一个时间比较就宣称整个协议已修好。
5. `VideoPresentation::update` 在替换 UI 图片后就调用 submission。现有 submitted_fps 是 UI 接受帧，不是 GPU 完成或面板扫描帧。真实呈现另由系统短窗口采集，两者不能互换。
6. 远端显示模式、串流目标、编码器名义帧率和手机显示节拍此前没有作为一组能力/配置协商。beta.14 的安卓能力上限只是这一缺口中的一部分，不能单独代表整条链路已重构。

Windows 被控端已装 4.0.0-beta.14，源码 1a7a822e650e60675509c7db686188581573ceb5；安卓已装 4.0.0-beta.14 / 40014，源码 91e98fdf918d2bcdb0a74262d50f10c39299b0fb，原绑定保留。Windows 驱动摘要、持久虚拟屏配置及物理主屏在程序更新前后核对一致。未新增、撤销虚拟屏。

安卓启动日志确认读取本机上限为 120.000Hz，FIFO、requested_frame_latency=3。新的实际 UFO 片段接收/解码/UI 中位数约 70/70.5/70.5FPS，系统呈现三个短窗口约 61.99/80.03/78.38Hz；因此没有达到目标。采样结束的画面出现展开的网页菜单、UFO 同步失败，不能当作固定场景的干净前后对照，也不能把 49→70 的数字变化归因为单项修改。

已读取更新后的主机日志：10:43:43 目标仍为 8.333ms；约一秒内 63 个新帧、56 个编码输出，捕获平均 6.243ms、编码平均 6.136ms、交接平均 1.884ms。它说明当时手机低帧与主机供帧不足同时存在，而非单凭 UI 计数判断手机被锁定。墙钟耗时包含调度等待，不能直接称为纯 GPU 编码耗时。

本轮近整屏原生负载窗口为 1888×1048，已自动退出。其提交频率约 119.58 次/秒，但前台激活未成功，部分同步统计约 57Hz；不能据此宣称测试源已稳定可见 120FPS，不能用这组 44FPS 替代 UFO 验收。

从安装前被控端 454811d82b01ec390212784870129074c7568d7b 到新包的累计差异还包含 session-transport 的既有调度修改，不仅是这轮 AMD 队列阈值。这也是前后归因必须核对完整安装源码范围的原因。

## 统一重构的运行约定

- 配置只有一个生效代次：远端显示 Hz、目标串流 FPS、本机呈现能力分别表达，协商后确认实际值；码率、分辨率或显示器变化触发明确的配置切换，不由多个 UI 回调各自改时钟。
- 同一 session/epoch/frame_id 贯穿数据通路；提交、排队、发送、解码、GPU 提交、完成和释放分别定义。旧代次的帧与通知不能解除新代次的信用或恢复新画面。
- 背压在编码前决定是否接收新捕获帧，避免先编码再因发送队列满而破坏参考链。采集、编码输出和发送分开推进，以明确的有界信用衔接，不把各阶段独立增大缓冲作为吞吐方案。
- 帧所有权同时支持 CPU 像素与平台原生表面。跨设备 GPU 工作以完成信号控制复用；通用 UI 不强制硬解输出先转 CPU 像素。硬件能力不支持时使用明确的受支持路径，不做隐式旧版本协议回退。
- 切屏、改模式、断连共用停止接收新帧、完成/取消在途工作、确认资源退役、切换代次的流程。保留现有退役失败拒绝拓扑修改的约束；虚拟屏的持久性与控制会话生命周期分离。
- xscs 继续承担账号、授权、绑定和能力发现；控制与非实时内容走 TCP，实时串流走 UDP。管理服务不混入逐帧数据通路，不恢复 QUIC 分支；账号和绑定数据迁移与媒体生命周期分开。

## 验收门槛

先用同一套生产实现锁定配置协商、旧代次隔离、发送背压、切换和资源释放的回归。再以相同源码组合、同一负载、相同分辨率和码率，运行 90/120/144/240Hz 档位；120Hz 手机的呈现目标按协商上限确定，不要求实际显示 240 帧。

逐帧核对主机输出、客户端接收、解码、实际 GPU 提交及延迟，覆盖持续运动、静止末帧、恢复运动、分辨率切换及重连；另检查键盘、菜单、鼠标和声音。性能与交互/资源释放必须在同一候选上一起通过。未通过前不发布“已修复”结论，不继续在用户机器叠加未经验证的参数实验。
