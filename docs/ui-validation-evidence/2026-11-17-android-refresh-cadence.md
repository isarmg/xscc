# Android 刷新率对照与候选修复（2026-11-17）

小米 13 通过 USB 确认已安装 4.0.0-beta.13 / 40013。复用 DISPLAY39，保持物理 DISPLAY1 为主屏；未添加、撤销显示器，未操作浏览器或全屏。每组约 17 秒，直接采集已有 UFO 画面，表中为逐窗口中位数；不同轮次有明显主机负载波动，不能据此断言某一刷新率必然更快。

| Windows 虚拟屏 Hz | 接收 / 解码 / UI FPS | UI 回调平均耗时 ms | present 平均耗时 ms |
| --- | --- | ---: | ---: |
| 90 | 85 / 84.5 / 85.5 | 4.115 | 2.027 |
| 120 | 49 / 50.5 / 49 | 3.870 | 2.365 |
| 144 | 79.5 / 79 / 77.5 | 4.050 | 2.609 |
| 244 | 59 / 59 / 57 | 2.950 | 2.017 |
| 240 | 42 / 42 / 43 | 2.425 | 2.080 |

244Hz 轮最初尝试从滚动菜单选择 240Hz，但 Windows 实际读回为 244Hz，故纠正记录，不把两者混为一谈。随后用系统 API 精确设置已存在虚拟屏的 240Hz，并核对物理屏模式及两屏位置不变；手机在该轮仍报告此前 244Hz 的控制状态，该轮仅用于主机产帧观察，不是干净的档位切换验收。

120Hz 的系统实际呈现三个短窗口为 93.37 / 88.97 / 69.71Hz，UI 回调仍约 120 次/秒。手机 thermal status 0，已有呈现缓冲调整后 present 多数约 2ms；不能继续把全部掉帧解释为手机显示被锁定 60/90Hz。

只读主机日志表明目标间隔仍为 8.333ms，但部分时段实际产出约 48–78 帧，编码平均耗时约 6.8–13.3ms、单次最大值超过 100ms，捕获约 4–5ms；手机接收、解码、UI 随之一起下降。Windows 同时存在较高 CPU 负载，当前证据没有排除调度/资源竞争，不把编码调用墙钟耗时误当成纯硬件编码时间。

## 候选改动

`vendor/hwcodec/cpp/ffmpeg_vram/ffmpeg_vram_encode.cpp` 的 AMD 路径原来提交到两个未完成帧后即等待输出，等待结束只剩一个在途帧。候选把同一有界阈值调为三个，允许保持两个在途帧以重叠转换和编码；实际缓冲引用仍由 FFmpeg 的完成/回收控制，不绕过 GPU 退役保护，也不更改其他编码后端。这是需要测量吞吐及延迟代价的候选，不是已通过的修复。

`apps/mobile/src/android_display.rs` 在启动时通过 Android 显示 API 读取与当前物理尺寸兼容的最高刷新率，保存在本应用不可变的能力值中；`AndroidImeBridge.java` 只增加只读查询，不更改手机系统设置。JNI 使用框架已锁定的同版本依赖 0.22.4，无新增底层库版本。`android.rs` 仅初始化该能力。

`session_view.rs` 的 Android MediaControls 路径把串流目标限制为远端刷新率与本机显示能力的较小值；虚拟屏仍可设置 144/240Hz。90Hz 对 120Hz 手机仍请求 90FPS，144/240Hz 对该手机请求 120FPS；240Hz 手机继续可请求 240FPS。读取失败时保持原目标，不猜测机型或强制 60Hz。非 Android 路径不变。

纯帧率选择放在已有 `display_state.rs`，新增一项行为回归，覆盖 90/120/144/240Hz、本地 240Hz 及未知值；与原有显示切换回归一起通过（2 项）。同一测试入口加入现有 Android 工作流。版本码递增到 40014。完整 Android 与 Windows 构建、安装及真实画面验收待续，尚未声称稳定 120FPS。
