# 串流模式

本分支以 Windows 主机与 Windows 客户端的高帧率、低延迟交互为首个目标场景。优先使用局域网直连、DXGI 采集、GPU 硬件编解码和纹理呈现。支持平台为 Windows 11 x86_64、Linux x86_64 Wayland、macOS 26 Apple Silicon、iOS/iPadOS 26 和 Android ARM64。

本分支移除文件传输、终端、打印、隧道、聊天、地址簿与云账户管理、摄像头查看、会话录像及上传、非文字剪贴板和旧 Sciter 界面。设备配对、认证加密、屏幕与系统声音、键鼠和文字剪贴板保留。

Android、iOS 和 iPadOS 只作为控制端；被控端仅面向 Windows、Linux 和 macOS。

## 第一阶段

在原生桌面远控工具栏中开启「串流模式」，选择 60、90 或 120 FPS。这个数值是目标上限；实际输出由显示器、编码器、客户端解码速度和网络共同决定。

模式拥有独立的帧率设置，不覆盖原有图像质量、自定义帧率或编码器偏好。关闭后恢复普通远控设置。

客户端在快速处理积压时合并呈现：依赖帧仍按原流程解码，只减少重复提交到渲染器的已解码图像。到达目标呈现间隔、队列接近排空或关闭模式时正常呈现。

采集线程的帧反馈等待使用同步通知，移除逐次创建异步运行时的开销。

这些改变是串流改造的起点。当前媒体仍通过 RustDesk 的可靠、有序链路传输；本分支尚未实现独立实时媒体通道，也不提供 Moonlight 协议兼容性。

## 连接

通过局域网发现选择主机，或输入 IP/域名，可附加监听端口。默认直连 TCP 端口是 21118，例如 `192.168.1.20`、`host.example.net:21118`、`[2001:db8::20]:21118`。

首次连接时，在主机关于页面核对指纹并确认，再进行会话认证。客户端保存该地址的主机身份；后续身份不一致时拒绝连接，需核实主机是否重装或更换后再移除旧信任记录。

主机地址必须可到达。跨公网使用可达的 IPv6 地址或配置端口映射；项目不提供协调、中继或打洞服务。

## Linux 平台

Linux 原生窗口只启用 GTK Wayland 后端，采集保留 Portal/PipeWire 与现有可选 DRM 路径。屏幕共享、输入授权和 GPU 缓冲导入分别取决于桌面后端能力；没有对应实现的全局光标移动和分辨率控制返回不支持。

## 后续媒体链路

控制与媒体分离：

- 现有认证和授权决定会话及设备访问权限。
- 可靠控制通道承载会话协商、输入、设备状态和重同步请求。
- 实时媒体通道承载带序号和时间戳的视频、音频，按帧期限重组和回收。
- 视频恢复与编码参考依赖一起设计：丢失参考帧时请求随机访问帧，不把任意关键帧标记当成无条件恢复点。
- 发包节奏、码率反馈和呈现节奏分别控制，避免大视频消息阻塞输入处理。
- 媒体通道须绑定已授权会话并具备认证加密、重放保护及资源上限。

当前使用强制加密的直接 TCP 连接；协调服务器、中继、NAT 打洞、TURN、KCP 和 WebRTC 连接路径已移除。实时媒体通道仍需独立实现。现有 DXGI 至硬编输入的 GPU 纹理路径继续利用；GPU 内部复制和渲染插件行为通过实机数据判断。

## 验收

先在同一对机器、相同分辨率、显示刷新率、编码器和网络下，对照普通模式、串流模式以及 Sunshine + Moonlight。

测试组合：

- 1080p60、1080p120、1440p60：持续运动画面与交互操作。
- 静态桌面、视频播放、快速滚动、全屏切换和重连。
- 客户端负载升高、网络短暂抖动、多个观看者中的一个变慢。
- GPU 路径与软件后备路径分别记录，避免把后备路径结果当成硬件路径表现。

每次记录：

- 两端系统、GPU、驱动版本、显示刷新率和实际传输方式。
- 实际采集、编码、解码、提交呈现 FPS，码率及刷新次数。
- 采集、编码、发送等待、解码和呈现提交的耗时分布。
- 编码队列长度及图像年龄；不能用帧数容量代替实际延迟。
- 同一方法测得的端到端响应延迟。

渲染回调完成只代表图像提交给渲染器，不等于屏幕已经显示。端到端延迟需要实际显示测量，不能把各线程耗时简单相加代替。
