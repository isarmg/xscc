# 避免过度防御性编程

本规范参考用户提供的 Rust 开发规范及 ZXS 审查报告，按 XSCC 的原生应用、内嵌管理与会话证明边界取舍。ZXS 报告中的文件位置、性能结论和重构方案不能直接当作 XSCC 的问题清单。

## 开发规则

1. 在网络、配置、磁盘首次读取、FFI 和公开库 API 入口解析外部输入。内部继续传递验证后的类型。
2. 格式验证与实时授权分开：类型能保证地址合法，不能保证租约尚未到期、连接仍在线或授权未被撤销。
3. 读取单个对端时借用当前授权观察，只复制要返回的绑定、地址或密钥。状态接口只投影脱敏字段。
4. 外部失败用 `Result` 处理，保留能供调用方决策的信息；内部不变量优先通过类型和控制流表达，确有必要时才用带原因的 `expect("invariant: …")`。
5. 简化要直接删除重复工作，保持接口、存储格式、持久化顺序和原生支持平台。新增 trait、缓存、后台任务或兼容分支必须有实际调用需求。
6. `checked_*`、`saturating_*`、`.ok()` 和 `validate_*` 只是审阅线索。逐项确认来源与语义，不做全仓库替换。

## 信任边界

| 入口或事实 | 验证与使用方式 |
| --- | --- |
| UI / IPC 注册参数、磁盘 settings | `ServerOrigin` 解析 HTTPS 或允许的本机/私网 HTTP 来源；内部保留该类型 |
| HTTP / WSS 响应 | 保留证书、大小、协议、绑定和凭据检查 |
| 授权观察 | 每次从当前观察检查连接、租约、角色、绑定及对端状态 |
| 本机私有存储 / IPC / FFI | 保留权限、对端身份、符号链接、长度及宿主安全检查 |
| 执行记录恢复与结果确认 | 保留持久化校验、去重、容量限制及确认顺序 |

## 本轮改造

`Settings.server` 直接保存 `ServerOrigin`，反序列化时完成来源验证。运行和解绑使用该类型，磁盘上的 `server` 字段仍是字符串，版本仍为 1。

单个目标查询和会话授权检查借用 watch 中的有效策略，只复制调用方需要的输出；状态接口直接投影脱敏字段，避免复制随后丢弃的会话密钥。对端查找仍为 O(P)，P 为授权对端数；单目标操作的额外分配不再随无关对端和密钥数量增长。原有断连、过期和撤权检查继续生效；此处没有新增缓存或 fsync。这是源码复杂度分析，未测量延迟或吞吐量。

旧 settings 文件仍可读取；有效但未规范化的来源会在状态输出中呈现规范形式，例如 `https://EXAMPLE.com:443` 转为 `https://example.com/`。

既有运行路径的改动范围：

| 生产文件 | 运行路径与必要性 |
| --- | --- |
| `crates/native-management/src/enrollment.rs` | 为来源类型提供边界反序列化，保持字符串格式并执行现有来源规则 |
| `crates/native-management/src/manager.rs` | 配置读取、注册同源比较、恢复与解绑复用类型；状态、目标与会话授权按需投影，消除重复解析和整表复制 |

## 审阅与验证

每次修改说明输入来源、验证位置、依赖的类型保证、改变的既有运行路径和复杂度。修改持久化路径时另说明 fsync 次数及提交顺序。

在仓库根目录运行：

```sh
cargo fmt -p xscc -p xscc-native-management -- --check
cargo test --locked -p xscc -p xscc-native-management
cargo clippy --locked -p xscc -p xscc-native-management --all-targets -- -D warnings
git diff --check
```

现有 Native management CI 配置为在桌面三平台执行管理库检查，并对 iOS / Android 做目标检查。单元测试与 Linux 检查不代表其它平台本轮已验收，也不代表捕获、媒体、输入或实机串流已经通过。

2026-10-26 本地 Linux 验证：两个管理包共 26 项测试通过，Clippy `-D warnings`、格式和 diff 检查通过；测试与 Clippy 使用锁文件并离线运行。覆盖了来源字符串序列化、旧 settings 读取、非法来源拒绝和既有授权观察失效等行为。未执行本轮其它平台、完整 GPUI 应用或物理设备验收。
